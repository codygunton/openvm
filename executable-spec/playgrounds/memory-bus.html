Memory Bus

Memory in OpenVM is verified using an offline checker protocol. Every memory access generates a pair of bus interactions: it receives the previous state (proving continuity) and sends the new state (for future access). Timestamp ordering ensures accesses happen in the correct sequence.
New: Memory Tuples

Each bus interaction carries (addr, data, timestamp). A read receives (addr, data, prev_ts) and sends (addr, data, current_ts) — same data. A write receives (addr, OLD_data, prev_ts) and sends (addr, NEW_data, current_ts).

New: Timestamp Ordering

For each access, the prover shows prev_timestamp < current_timestamp. If you can't prove this, you might be reading data from the future.

New: Boundary Chip

The boundary chip initializes each address at timestamp 0 (sends initial tuples) and finalizes by absorbing the last state (receives final tuples). This closes the bus: all sends must balance all receives.

Constraints
  • C1 Timestamp ordering prev_ts < current_ts for each user operation user ops
  • C2 Bus balance Σ sends = Σ receives (multiset equality) global
  • C3 Read consistency read data must match last-written data at that address read ops

Bus Ledger

Every operation generates bus interactions. All sends must be matched by a receive with the same tuple.

What happens when you break things

Try changing the data in the READ operation. The bus won't balance because the read's receive tuple won't match the write's send tuple.

Try swapping timestamps so a read happens "before" a write. The timestamp ordering constraint will fail.

Try changing a write's data without updating the subsequent read. The read consistency constraint (C3) will fail, and the bus ledger will show unmatched tuples.
